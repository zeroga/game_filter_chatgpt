# Feedback Intake Rule

本文件定义用户对游戏发表意见时的通用理解流程。

它不是保存流程。它必须在收到游戏反馈后立刻执行，并且早于推荐、解释、更新清单、候选审计和保存流程。

## 触发条件

当用户对具体游戏、系列、版本、平台或机制发表意见时，视为游戏反馈。

典型输入包括：

```text
玩过 / 通关 / 弃坑 / 退款 / 正在玩
终盘无聊 / 后期重复 / Build 浅 / 联机不行 / 不能联机
某机制好 / 某机制差 / 某版本改了 / 某平台不可用
```

## 固定流程

```text
1. 先联网确认用户说的对象和事实。
2. 再拆分反馈的数据层。
3. 再合并进当前推荐、解释、更新清单或保存流程。
```

## 第一步：联网确认对象和事实

收到游戏反馈后，必须立刻联网核对，不得等到用户要求保存时才核对。

至少确认：

```text
游戏对象：用户说的是哪个游戏、别名、系列、版本或 DLC。
平台范围：PC、主机、移动端、跨平台版本是否一致。
机制事实：用户提到的联机、终盘、刷装、Build、DLC、服务状态等是否存在。
时效状态：该事实是否被补丁、DLC、停服、平台迁移或版本更新改变。
近期反馈：近期玩家评价或可信社区是否有相近反馈。
```

用户主观体验不能被外部资料否定；但客观结构、版本状态、联机结构、服务状态和评价趋势必须外部核对。

## 第二步：拆分反馈的数据层

同一句反馈可能同时包含多层信息，必须拆开判断，不能整句归入单一数据层。

### 公共画像候选

可跨用户复用的游戏事实、机制特征、结构风险、版本状态、联机结构、内容深度、终局问题、评价趋势等。

公共画像候选只有经过联网核对后，才允许写入：

```text
public.memory_items
```

如果只有用户单人体验，尚未外部核对，只能标记为公共画像候选，不能直接写成共享事实。

### 用户游玩记录

用户明确说玩过、通关、弃坑、退款、正在玩、已刷穿、没玩下去等，属于个人游玩记录。

写入：

```text
public.user_preference_items
item_type = played_record
```

### 用户偏好 / 反馈覆盖

用户表达主观体验、喜好、厌恶点、实际可用性体验或对某机制的接受度，属于用户偏好或反馈覆盖。

单游戏反馈写入：

```text
public.user_preference_items
item_type = game_feedback_overlay
```

可跨游戏稳定复用的偏好另写：

```text
public.user_preference_items
item_type = stable_preference
```

### 用户场景状态

如果反馈影响当前场景下的推荐、等待、排除、低优先或仅作参考，写入：

```text
public.user_scenario_items
user_key + namespace + scenario_code + game_key
```

## 示例

用户说：

```text
FF 起源已玩，终盘战斗比较无聊，且没法联机。
```

必须先核对：

```text
FF 起源 = Stranger of Paradise: Final Fantasy Origin。
当前平台/商店页是否仍标注联机。
联机是否有平台、任务、进度、DLC、网络、服务器或匹配限制。
终盘重复、支线重复、刷装乏味是否有外部评价或近期玩家反馈支持。
```

再拆分：

```text
公共画像候选：
- 若外部核对支持，可记录终盘 / 支线 / 刷装阶段重复和乏味风险。
- 若官方仍支持 Online Co-op，不能写成“无联机”；只能记录联机可用性需按平台和场景核查。

用户游玩记录：
- 用户已玩 FF 起源。

用户偏好 / 反馈覆盖：
- 用户认为终盘战斗无聊。
- 用户实际体验为没法联机。

用户场景状态：
- 当前场景中不作为新推荐。
- 可作为终盘重复风险和联机可用性风险的负面参考。
```

## 禁止行为

```text
不能把用户整句反馈直接整体写入 played_record。
不能把用户个人体验未经核对直接写入 public.memory_items。
不能忽略用户反馈中可公共化的游戏结构信息。
不能只因反馈来自个人体验就完全不考虑公共画像更新。
不能等到用户说保存时才联网核对反馈中的事实和时效。
不能在推荐、解释、更新清单或候选审计中跳过反馈理解和分层拆分。
```

## 与保存流程的关系

feedback_intake 负责理解用户反馈和数据层拆分。

save_flow 只负责用户明确要求保存后的摘要、确认和写入控制。

是否保存不影响 feedback_intake 的即时执行；用户不保存时，当前对话结论仍应按拆分后的结果参与推荐和解释。
