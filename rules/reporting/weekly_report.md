# Profile 级游戏推荐与资讯周报

本文件是游戏推荐与资讯周报的唯一专项规则真源。周报路由、新游雷达、资讯筛选、增量比较、调度和自动写入边界不再拆分为其他规则文件。

## 能力入口与读取边界

项目规则读取完成后必须提示：

> 本项目支持在确认 profile code 后配置游戏推荐与资讯周报，可自定义推送时间、平台、资讯类别和详细搜索范围。

此时只介绍能力，不读取个人配置。用户主动提供 profile code、完成 `profile_routing` 并确认 `user_key` 后，才允许查询 `public.user_report_subscriptions`；不需要先确认 scenario code。

推荐开始前的配置预检必须显示：启用或暂停、推送时间和时区、详细内容范围、新游雷达设置、资讯类别、下次计划运行时间、配置与实际 Automation 是否同步，以及当前场景是否在详细搜索范围内。没有配置时显示“当前未配置周报”。查询失败只显示降级提示，不阻断正常推荐。同一对话已展示且配置未变化时不重复。

## 配置模型

第一版每个 `user_key + namespace + report_type` 只允许一条配置，`report_type = weekly_game_report`，不使用 `report_code`。至少支持：

- `enabled`；周几、时间、IANA 时区；每周必发或无重要内容时跳过。
- 详细推荐搜索覆盖：全部场景、仅包含指定场景、排除指定场景。
- 平台范围。
- 新游雷达开关、数量、时间窗口。
- 是否包含 EA、试玩、测试和没有中文的游戏。
- 资讯类别；是否包含价格与促销；传闻默认关闭。

摘要范围始终覆盖该 profile 下所有实际场景，不受详细搜索范围限制。详细搜索范围只控制推荐变动研究与资讯深度。新游雷达默认 profile-wide，综合全部稳定偏好、游玩记录、正负面参考和所有场景需求。

创建、修改、暂停、恢复和删除配置必须按 `rules/save_flow.md` 输出保存摘要并等待确认。

## 正文结构

### 1. 报告信息

只显示报告周期、生成时间、profile 和主要配置范围。

### 2. 所有场景推荐清单

- 枚举该 `user_key` 的全部实际场景，排除场景类型模板和 `legacy_imported_status`。
- 每个场景完整列出数据库中正式 `state = recommended` 的游戏名，不重复理由、不限数量、不强制填满。
- 同一游戏可在多个场景出现；无推荐项显示“暂无推荐”；未变化场景仍保留完整清单。
- 首次运行只建立基线，不把已有项目标记为新增。
- 尚未确认的变动建议不得混入正式清单；只有保存完成后，下一期摘要才反映正式变化。

### 3. 推荐变动建议

只详细说明相较上期新增或证据继续变化的建议：新增或移出推荐、其他状态转为推荐、推荐转为等待/待查/低优先/排除、适用场景增减。同一游戏影响多个场景时合并介绍。

每项必须包含游戏名称、涉及场景、当前正式 `state`、建议 `state`、变化原因、触发事实或用户记录、关键风险、来源和核查日期，并明确标记“尚未写入”。用户未确认的建议可作为待处理项保留，但不得在下期伪装成本周新变化。

### 4. 新游雷达

覆盖本周公布、新开放商店页或预告、即将或最近发售但未入候选库、新进入 EA/测试/试玩，以及正式公布平台、联机模式或项目重启的游戏。

每款至少包含：游戏名称、预计发售时间和平台、当前阶段、核心玩法/成长/联机结构、感兴趣依据、命中的偏好与正面参考、潜在负面冲突、与现有场景关系、`高度关注 / 一般关注 / 证据不足` 标签、来源和核查日期。新游雷达判断兴趣，不等同正式推荐；若已完成完整候选审计并进入推荐变动建议，则不重复详细介绍。

### 5. 游戏资讯

只报道与已玩/正在玩、正式推荐/等待/待查/关注，或稳定偏好和所选平台高度相关的游戏。类别包括发售延期取消、大型更新/DLC/路线图、联机/跨平台/服务器/匹配变化、平台移植、订阅库进出、停服/开发异常/支持变化，以及可选价格促销。

每条回答：发生了什么、为何与用户有关、影响哪些游戏或场景、是否可能改变推荐结论。默认排除普通公司新闻、财报、电竞、营销稿和无可靠来源传闻。已进入新游雷达的公告只交叉引用。

### 6. 近期观察

只列即将发售、测试、重大更新或需复查事项及预计时间，不重复前文。

### 7. 核查异常

仅在来源冲突、查询失败、数据过期或证据不足时出现。部分网络或来源失败时仍应生成降级报告，并明确受影响的范围。

## 后台审计与事实核查

每次运行必须读取共享游戏画像、用户稳定偏好、反馈覆盖、正负面索引、全部 `played_record` 和相关场景正式状态。已玩、退款、弃坑、正在玩等状态必须参与候选审计。候选缺少现有规则要求的审计字段时，不得进入推荐变动建议。

当前发售、版本、平台、联机、DLC、价格和近期评价必须联网核查。用户主观反馈优先于外部主观评价，客观结构仍需外部验证。`waiting`、`investigate`、`low_priority` 等状态仅在影响变动建议或近期观察时进入正文。

## 增量与去重

`last_snapshot` 至少保存正式清单基线、已报告建议的稳定标识与证据版本、新游/资讯去重标识、待用户处理建议和本期核查时间。首次运行建立基线。后续只有建议状态、证据或影响场景发生变化时，才重新详细展开待处理建议。

## 调度、同步与单次运行

Supabase 保存业务配置和预期调度；ChatGPT Automations 保存实际执行计划；`automation_id` 映射两者。定时任务 prompt 只包含稳定订阅标识和运行规则，不写死完整可变配置，每次运行重新读取配置。

创建、修改时间、暂停、恢复或删除时必须同步两边，并分别回查 Supabase 与实际 Automation。不一致时更新 `sync_state`，在配置预检中明确告警。

单次运行顺序：

1. 读取项目最新规则和已确认订阅配置。
2. 获取该 `user_key` 全部实际场景；未来新增场景自动纳入。
3. 读取共享画像、用户偏好、游玩记录和全部相关场景状态。
4. 生成所有场景正式推荐清单摘要。
5. 按配置联网寻找推荐变动、新游和相关资讯。
6. 完成候选审计和事实核查，与 `last_snapshot` 比较并去重。
7. 生成并推送周报；部分失败时生成降级报告。
8. 只回写已授权的周报运行元数据和快照。

## 写入边界

创建或修改配置仍需保存摘要、用户确认、写入和回查。用户确认创建周报时，可以同时授权未来定时任务自动更新：`last_snapshot`、`last_run_at`、`last_success_at`、`last_error`、`sync_state`。

定时任务不得自动接受推荐变动，也不得写入 `public.user_scenario_items`、`public.user_preference_items`、`public.memory_items`、GitHub 场景快照或 GitHub 规则文件。推荐变动只有用户确认后，才能按现有 `save_flow` 写入正式数据层。

## 验收与必测场景

至少验证：未配置、启用、暂停、同步异常；首次与第二次增量运行；新增场景自动进入摘要；无推荐项场景；新游命中多场景；新游升级为变动建议时不重复；未确认时正式清单不变；确认保存后下期反映变化；网络部分失败；定时运行后只有允许的周报运行字段变化；新表启用 RLS 且客户端角色无访问权。
