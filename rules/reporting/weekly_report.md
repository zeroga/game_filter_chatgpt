# Profile 级游戏推荐与资讯周报

本文件是游戏推荐与资讯周报的唯一专项规则真源。周报路由、新游雷达、资讯筛选、增量比较、调度、删除恢复和写入边界不再拆分为其他规则文件。

## 能力入口与两阶段预检

项目规则读取完成后必须提示：

> 本项目支持在确认 profile code 后配置游戏推荐与资讯周报，可自定义推送时间、平台、资讯类别和详细搜索范围。

此时只介绍能力，不读取个人配置。用户主动提供 profile code、完成 `profile_routing` 并确认 `user_key` 后，才允许查询 `public.user_report_subscriptions`；不需要先确认 scenario code。

预检分为两个时点：

1. **profile 确认后**：只展示未配置，或启用/暂停状态、推送时间与时区、详细内容范围、新游雷达设置、资讯类别、下次计划运行时间、配置与实际 Automation 是否同步。此时没有 scenario code，不得判断“当前场景是否在详细范围”。
2. **scenario 确认后**：再展示该 `scenario_code` 是否纳入详细搜索范围；不重复未变化的总体配置。

查询失败只显示降级提示，不阻断正常推荐。同一对话中同一阶段已经展示且配置没有变化时不重复。

## 配置模型

第一版每个 `user_key + namespace + report_type` 只允许一条配置，`report_type = weekly_game_report`，不使用 `report_code`，也不新增独立运行历史表。配置至少支持：

- `enabled`；周几、时间、IANA 时区；每周必发或无重要内容时跳过。
- 详细推荐搜索覆盖：全部场景、仅包含指定场景、排除指定场景。
- 平台范围。
- 新游雷达开关、数量、时间窗口。
- 是否包含 EA、试玩、测试和没有中文的游戏。
- 资讯类别；是否包含价格与促销；传闻默认关闭。

摘要范围固定覆盖该 profile 的全部正式场景，不受详细搜索范围限制。详细搜索范围只控制推荐变动研究与资讯深度。新游雷达默认 profile-wide，跨场景综合全部稳定偏好、游玩记录、正负面参考和所有正式场景需求。

创建、修改、暂停、恢复和删除配置必须按 `rules/save_flow.md` 当次展示写入内容并等待当次确认。不存在创建时授予以后每期持续写入权限的机制，不新增 `runtime_write_authorized` 或同类长期授权字段。

## 正式场景枚举真源

已由用户确认创建且当前启用的 `weekly_game_report` Automation 定时触发时，必须先用 prompt 中的稳定订阅标识只读定位唯一订阅记录，再使用该记录中已确认的 `user_key`。仅在这种已确认订阅触发的定时运行中，无需用户当轮重新提供 profile code 或 scenario code；任务只能为生成周报而只读遍历正式场景，不得把遍历结果解释为当前场景选择，也不得用于普通交互式推荐、用户切换或任何写入。

每个正式场景必须在 `public.user_scenario_items` 存在定义记录：

```text
user_key = <user_key>
namespace = game_filter
scenario_code = <scenario_code>
game_key = __scenario_definition__
state = scenario_definition
```

周报只能以这些定义记录枚举全部正式场景。`memory/scenario_types/*`、GitHub 用户快照、`legacy_imported_status`、仅有普通游戏状态但没有定义记录的历史 scenario code 都不能直接作为枚举真源。

新场景创建流程必须同步创建定义记录，即使场景没有任何游戏记录或推荐项，也必须进入周报摘要并显示“暂无推荐”。旧场景缺少定义记录时，先按 `rules/routing/scenario_routing.md` 核对身份和口径，再按 `save_flow` 展示回填内容、取得用户当次确认、写入并回查；回填完成前不得把它悄悄计入正式场景，也不得因回填待处理而删除其旧游戏状态。

## 周报正文结构

### 1. 报告信息

显示按计划周期稳定计算的 `report_period`、生成时间、profile、主要配置范围，以及本期 `report_generated` / `report_written` 状态。每个新周期创建全新的期内状态，不得继承上一期两个标志。

### 2. 所有正式场景推荐清单

- 按 `__scenario_definition__ + scenario_definition` 定义记录枚举全部正式场景。
- 每个场景完整列出数据库中正式 `state = recommended` 的游戏名，不重复理由、不限数量、不强制填满。
- 没有任何游戏记录或没有推荐项的场景显示“暂无推荐”；未变化场景仍保留完整清单。
- 同一游戏可以在多个场景出现。
- 尚未确认的本期建议不得混入正式清单；只有当次确认并保存成功后，后续周报才显示正式变化。

### 3. 推荐与候选状态变动建议

方案一固定边界：周报只提出变动，不自动修改正式推荐清单或任何候选状态。

相较最近一次经用户确认保存的 `last_snapshot`，列出新增推荐、移出推荐、`waiting` / `investigate` / `low_priority` 等状态转为推荐、推荐转为其他状态，以及适用场景增减。同一游戏影响多个场景时合并介绍。

每项必须包含游戏名称、涉及场景、当前正式 `state`、建议 `state`、变化原因、触发事实或用户记录、关键风险、来源和核查日期，并明确标记“尚未写入”。未处理建议允许在后续周期再次出现；不得伪装为已经写入的正式变化。

### 4. 新游雷达

覆盖本周公布、新开放商店页或预告、即将或最近发售但未入候选库、新进入 EA/测试/试玩，以及正式公布平台、联机模式或项目重启的游戏。

每款至少包含游戏名称、预计发售时间和平台、当前阶段、核心玩法/成长/联机结构、感兴趣依据、命中的偏好与正面参考、潜在负面冲突、与正式场景关系、`高度关注 / 一般关注 / 证据不足` 标签、来源和核查日期。新游雷达是 profile 级跨场景兴趣判断，不等同正式推荐；若已完成完整候选审计并进入变动建议，则不重复详细介绍。

### 5. 游戏资讯

只报道与已玩/正在玩、正式推荐/等待/待查/关注，或稳定偏好和所选平台高度相关的游戏。每条回答发生了什么、为何与用户有关、影响哪些游戏或场景、是否可能改变推荐结论。默认排除普通公司新闻、财报、电竞、营销稿和无可靠来源传闻。已进入新游雷达的公告只交叉引用。

### 6. 近期观察

只列即将发售、测试、重大更新或需复查事项及预计时间，不重复前文。

### 7. 核查异常

仅在来源冲突、查询失败、数据过期或证据不足时出现。部分网络或来源失败时仍生成降级报告并明确受影响范围。

### 8. 本期建议写入内容

每期周报必须附带清晰、完整、可逐项选择的写入差异，至少包括：

- 推荐清单变动。
- 候选状态变动。
- 拟保存为 `last_snapshot` 的本期快照差异。
- 如拟落库，当前 `report_period` 的 `report_generated`、`report_written` 以及其他运行字段变动。

每项列出目标层/表、逻辑键、当前值、建议值和理由。生成时这些全部是建议，均标记“尚未写入”。不得展示范围外写入，也不得用笼统确认扩展写入范围。

## 后台审计与事实核查

每次运行必须读取共享游戏画像、用户稳定偏好、反馈覆盖、正负面索引、全部 `played_record` 和全部正式场景状态。已玩、退款、弃坑、正在玩等状态必须参与候选审计。候选缺少现有规则要求的审计字段时，不得进入变动建议。

当前发售、版本、平台、联机、DLC、价格和近期评价必须联网核查。用户主观反馈优先于外部主观评价，客观结构仍需外部验证。

## report_period、标志与确认基线

- `report_period` 不是随机运行 ID。它由订阅的 `schedule_ical` 所确定的计划执行周期及订阅的 IANA `timezone` 稳定计算，规范值使用 `weekly_game_report:<周期计划触发日在订阅时区的 YYYY-MM-DD>`；周期边界和日期均按该时区计算。
- 同一订阅在同一计划周期内的首次运行、失败重试、重复触发和重新投递必须复用同一 `report_period`；只有进入下一个计划周期才生成新值。夏令时等偏移变化以 IANA 时区规则解释计划周期，不得以服务器时区另行切分。
- `report_period` 只标识某订阅内部的计划周期，不是跨订阅全局键。识别一份周报必须结合稳定订阅标识（订阅记录 `id`，并以 `user_key + namespace + report_type` 校验）与 `report_period`；不同订阅即使周期字符串相同也不得互相覆盖。不得为此新增独立运行历史表。
- `report_generated` 表示该期内容已经生成。`report_written = true` 仅表示用户已经对本期建议作出明确处理，且其当次明确确认写入的全部项目均已成功写入；它不表示用户接受本期全部建议。新一期两个标志重新从 `false` 开始，不继承上期值。
- 周报生成阶段严格只读。生成报告、设置输出中的 `report_generated = true` 或提出落库建议，都不得修改 Supabase、GitHub、Automation 或正式推荐数据。
- 两个标志如果需要落库，必须列入本期“建议写入内容”，并获得用户当次明确确认；它们不是自动写入例外。
- `last_snapshot` 是“最近一次经用户确认且成功写入的周报快照”，不是最近一次自动生成结果，只能纳入本期实际获确认并成功写入的内容。未确认或明确拒绝的项目不得进入正式数据或 `last_snapshot`，以后仍可按规则再次出现。
- 首次生成时，以当前正式场景和正式推荐清单建立拟议基线，不把历史项目误报为新增；在用户确认保存前，这个基线只存在于报告建议中，数据库仍保持不变。
- 部分确认时只处理确认项；当次确认的任一写入失败，`report_written` 不得为 `true`，且 `last_snapshot` 不得声称包含失败项。用户拒绝本期全部建议且没有确认任何写入时，不发生写入，`report_written` 保持 `false`；拒绝可在报告中说明，但不得用该字段伪装为发生过成功写入。未确认、明确拒绝或失败的建议仍可在后续周期再次出现，不增加第三个处理状态标志或独立历史表。

## 逐期只读生成与当次确认闭环

1. 读取最新规则、订阅配置及最近一次已确认的 `last_snapshot`。
2. 只按正式定义记录枚举全部场景，读取共享画像、用户偏好、游玩记录和场景状态。
3. 按配置联网研究并完成候选审计，与确认基线比较。
4. 生成带唯一 `report_period` 的周报及完整“本期建议写入内容”；本阶段不得写入任何系统。
5. 用户阅读后可以**全部确认、部分确认或拒绝**。只有本期展示且被当次明确确认的具体项目才能进入 `save_flow`；未确认和明确拒绝的项目均不得写入。
6. 部分确认时只写确认项；全部确认也不得超过本期已展示范围。所有实际写入逐项回查，`last_snapshot` 只纳入实际获确认并成功写入的内容。
7. 当次明确确认写入的全部项目均成功后，才可在当次确认范围内将 `report_written` 置为 `true`；任一确认写入失败时不得置为 `true`。拒绝本期全部建议且没有确认任何写入时不发生写入，`report_written` 保持 `false`。

## 调度、同步与删除恢复

Supabase 保存业务配置和预期调度；ChatGPT Automations 保存实际计划；`automation_id` 映射两者。定时任务 prompt 只包含稳定订阅标识和运行规则，每次运行重新只读读取配置及其中已确认的 `user_key`。定时触发只允许执行只读生成和投递，不要求当轮重新路由 profile / scenario，也不获得任何持续写入权限。

创建、修改时间、暂停或恢复时，必须按当次确认同步两边并分别回查；不一致时保留可恢复配置，通过 `sync_state` 和 `last_error` 记录原因并显示重试入口。

删除必须按以下顺序执行：

1. 用户看到删除影响范围并当次确认；范围必须预先包含 `pending_delete`、成功终态，以及失败时写入 `sync_state` / `last_error` 的可恢复审计变动。
2. 将订阅置为可恢复的 `pending_delete` 同步状态并回查，不先物理删除记录。
3. 删除对应 Automation 并回查确已不存在。
4. Automation 删除成功后，才删除 Supabase 订阅记录，或按用户确认的策略将其停用并标记 `deleted`。
5. 任一步失败都保留订阅记录及 `automation_id`，写明 `sync_state`、`last_error` 和失败步骤；不得遗留无法追踪的孤立任务。
6. 重试入口从记录的失败步骤继续；恢复入口可取消 `pending_delete`、复核 Automation 状态并恢复到一致的启用或暂停状态。重试或恢复同样需要展示影响范围并取得当次确认。

## 禁止写入边界

周报不得自动写入 `public.user_scenario_items`、`public.user_preference_items`、`public.memory_items`、`public.user_report_subscriptions`、GitHub 文件或 Automation。创建周报时的确认不能解释为以后每期持续授权。正式推荐清单、候选状态、确认快照、运行标志和错误状态的每次写入，都必须属于当期已展示并获确认的范围。

## 验收与必测场景

- 未配置、启用、暂停、同步异常和查询失败降级。
- profile 确认后只展示总体配置；scenario 确认后才判断详细范围。
- 只有正式定义记录进入摘要；场景无任何游戏记录或推荐项时仍显示“暂无推荐”。
- 首次生成前后没有未经确认的写入，历史项目不误报新增，拟议基线清晰展示。
- 每期附带推荐、候选状态、快照和期内标志的清晰建议写入差异。
- 支持全部确认、部分确认和拒绝；写入不超过当期展示并获确认的内容。
- 未确认或写入失败时，正式推荐和已确认 `last_snapshot` 保持不变，未处理建议可以再次出现。
- 新一期不继承上一期的 `report_generated` / `report_written`。
- 新游雷达跨全部正式场景工作，且与推荐变动和资讯不重复完整介绍。
- 删除任一步失败均保留可恢复、可追踪记录，不留下孤立 Automation 或无映射订阅。
- 不新增运行历史表；目标新表启用 RLS 且客户端角色无访问权。
